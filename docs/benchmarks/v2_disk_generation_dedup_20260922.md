## 内容差分：四个发布产物逐字节一致

本次复测的 harness 在计时区之外对四个发布产物（CSF 文本、CSF Parquet、descriptor
Parquet、header）记录 SHA-256，并在两种策略的计数、发布长度**或任一摘要**不一致时拒绝
写出报告。结果：B1 与 B2 上，两种策略、两种 codec 的全部运行发布**完全相同的内容**——

| 产物 | B1 SHA-256 | B2 SHA-256 |

| descriptor Parquet | `a9163c371f05…` | `28de0896cbbc…` |

## 结论

1. **跳过精确去重链路把 B1 从 13.271 秒降到 9.263 秒（−30.2%），B2 从 4.656 降到
   2.914 秒（−37.4%）**；省下的全部落在去重阶段本身（B1 4.167 → 0.005 秒，B2
   1.694 → 0.001 秒），生成、合并、还原三段在两种策略下相同。按计划要求，这一项单列，
   不冒充其它阶段的加速。与 `bbcd714` 轮（−32.4% / −38.5%）在同机同扩展上复测一致，
   差异在本机日间波动内。
2. **scratch 峰值下降约 50%**（B1 2142.5 → 1073.3 MiB，B2 999.9 → 506.1 MiB），
   减少的正是根桶：去重阶段的临时写入从 1069.8 MiB 降到 0.3 MiB（B1）、496.0 降到
   0.1 MiB（B2）。剩下的 0.3/0.1 MiB 是幸存位图本身——merge 仍按发布顺序读取它。
3. **组合配置把 scratch 压到 segment 量级**：verified_unique + zstd 时 B1 scratch
   峰值 12.0 MiB（相对 exact+none 的 2142.5 MiB 减少 99.4%），B2 为 4.5 MiB
   （相对 999.9 MiB 减少 99.6%）。这正是重新表述后的 P2b 验收条件所要求的形态。
4. 组合配置的端到端代价是 zstd 的解压：B1 9.263 → 9.882 秒（+6.7%），B2 2.914 →
   3.219 秒（+10.5%），全部出现在合并阶段（2.794 → 3.445、1.324 → 1.657 秒）。
5. **RSS：已验证路径不高于精确路径**（B1 233.7 对 240.4 MiB，B2 389.3 对 433.0 MiB，
   均 none codec）——不再构建按哈希分组的桶内行缓存；受管内存峰值两者相同（B1 62.0、
   B2 130.4 MiB），因为它由在途任务数决定。
6. 相对计划基线 `7ad18b1` 的 8 线程（B1 14.403 秒、B2 4.825 秒），组合配置为 9.882 秒
   （B1，−31.4%）与 3.219 秒（B2，−33.3%）。P4 的"累计 ≥2×"仍是未达成的调研目标，
   剩余空间在合并/还原两段（B1 合计 9.1 秒）。

## 未测量与边界

- 目标机器与目标文件系统；本机 NVMe/APFS、页缓存未清空，macOS 无 `process_io`。
- 递归分桶：两种输入都没有触发（根桶行数远低于叶桶上限），因此"跳过根桶"节省的是
  根桶那一轮写入/读取，递归层从未参与。
- 已验证路径的正确性依据是 [V2_GENERATION_UNIQUENESS.md](../V2_GENERATION_UNIQUENESS.md)
  的证明与 `tests/p6a_*` 的穷举；本页是它在真实输入上的差分与计量——四个产物的
  SHA-256 一致是**证据**，不是证明本身。
- 反例形态（同一 segment 被排两次）在本页的输入中不可达，它由
  `a_repeated_segment_is_only_removed_by_the_exact_path` 单测覆盖：那种输入下两条
  路径确实不同，因此快速路径的适用范围来自构造，而不是来自"没见过重复"。
