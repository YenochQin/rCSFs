# Gd I direct-CSFG validation and timing — 2026-10-30

Status: completed file-generation benchmark; no SCF/RCI calculation. Source is
rCSFs base `4e57b463f6ad1599fdc5a6a27bf7e0c6c933eff6` plus the uncommitted CSFG implementation.
This is a local development wheel, not a published release.

## Purpose and setup

The question was whether Rust can directly generate the same CSFG representation
as GRASPG for the existing Gd I SD model, while avoiding full-CSF intermediates.
The expected correctness target was **1,125,587 CSF(G) records**, expanding to
**11,299,739 CSFs**, with byte-identical GRASPG-compatible output. Runtime was
unknown before implementation; no speedup factor was an acceptance assumption.

- CPU: AMD Ryzen 7 7800X3D, eight logical CPUs available.
- Rust: rustc 1.99.0, release opt-level 3, LTO; local CPython 3.15 wheel.
- GRASPG baseline: e157d9f integrated in suite 50ca581, GNU Fortran 16.2.1,
  Release `-O3`, one process.
- Same physical reference, inactive core 4, labeling `6s,5p,5d,4f`, active
  `10s,9p,9d,8f,8g`, 2J=2..12, SD. The [guide](../CSFG_GENERATION.md) contains
  the complete TOML; 5s², 5p⁶ and 6s² remain inactive.
- Timed CLI invocations ran sequentially in fresh calculation directories on
  the workspace filesystem. Timings include process startup, generation and
  file output; exclude compilation, hashing, validation and optional expansion.
- Installed-wheel runs used `rcsfs csfggenerate` without `PYTHONPATH`; thus these
  numbers do not depend on accidentally importing a different checkout.
- Native extension SHA-256: `8a566e2490ed498da9c25beb26600cc782700e0ec908f33c48a3aba52fbf451a`.

The installed-wheel 8-thread median is **1.229 s**. Relative to the two
single-run Fortran measurements, the observed elapsed-time ratios are about
**403×** and **233×**.
These are local observations, not a cross-machine performance guarantee.
The full-CSF row represents the same physical space but writes a different,
larger representation; it is not a same-output algorithm benchmark.

The first wheel run reports planning 0.023 s,
angular generation 0.050 s, and writing
1.060 s. Text output dominates this case. The benefit
comes chiefly from generating only representative states and avoiding the
Fortran intermediate-list processing, rather than from scaling to eight threads.

## Exact output validation

All four installed-wheel runs match the independent GRASPG reference hashes:

| Artifact | Bytes | SHA-256 |
| --- | ---: | --- |
| `rcsfg.out` | 268650625 | `4ea7b710ad4b8bedcd5740ccc9bd513a63f225064f0e9bbfa3ea9f4280807187` |
| `rlabel.out` | 134 | `ab0181ae17f4e54365eab601fd5b0721ff939edc95393bff30bd51a40c3cfc30` |

The planner enumerates **7,154 physical occupations**, verifies their exact
non-overlapping expansion coverage, and generates **767 representative
occupations**. Type 1..5 record counts are **15,961; 169,580; 522,278; 288,969;
128,799**. The 15,961 type-1 records are ordinary labeling-space CSFs; the other
1,109,626 are generators.

The unmodified GRASPG `rcsfgexpand_csfg` was also run on the Rust output. Its
expanded file is 2,728,150,642 bytes with SHA-256
`c9105f15a68e7d1adbe7ecb0dd62607772f317f21fc688bfc7bff4e84a7e718e`, exactly matching
the earlier Fortran-expanded file. Expansion took 12.598 s and is
not included in the direct-CSFG timings.

The original ordinary n-ordered `.c` is not byte-identical to the CSFG expansion:
its orbital/coupling order differs, and the target calculation file has zero/first
space ordering. The earlier independent scan matched all 41,990 occupation/Jπ
group dimensions. The present byte comparisons are deliberately against the
same GRASPG representation, not a renaming of the old CSF basis. Existing mixing
coefficients cannot be reused solely on the basis of equal counts.

## Checks, artifacts and limits

- Rust library unit tests: **76 passed**.
- Python suite: **386 passed**, plus **21 subtests**.
- Ruff, basedpyright (zero errors/warnings/notes) and Rust formatting passed.
- A small stored Fortran fixture covers all five types. Maintained tests also
  cover thread invariance, duplicate/distinct references, minimum occupations,
  closed cores, one-radial-orbital cases, invalid input and partial publication.
- Local wheel build and installation into the rCSFs-owned environment succeeded.
  The shared Tools environment was not changed.

Raw inputs, CLI logs, timings, hashes, the native-library fingerprint and generated
large files remain in ignored `temp/gd_i_csfg_2026-10-30/`. `summary.json` is the
machine-readable index; `benchmark.py` reproduces the timed commands. The earlier
Fortran measurements remain in the workspace Gd benchmark directory. These local
artifacts are not required by CI or included in source commits.

The implemented scope is a common continuous S/SD space with an explicit labeling
space. Arbitrary radial restrictions, differing VV/CV/CC range unions, more than
two correlation electrons, bounded-memory CSFG generation and CSFG descriptors
remain outside the first version. No angular-matrix/SCF/RCI performance or physical
accuracy claim follows from this generation benchmark. The next validation step
for a production calculation is the full GRASPG consumer chain with consistent
orbital and coefficient ordering.
