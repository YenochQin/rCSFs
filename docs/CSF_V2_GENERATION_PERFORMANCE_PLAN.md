## 已实施内容（P0a/P1）

以下内容已经进入当前代码和维护测试；它们不是后续阶段的预期目标。

- **P0a 观测和基准入口**：`scripts/benchmark_v2_generation.py` 可接收任意 transcript，输出可保存的 JSON。磁盘路径现在分别记录 `enumeration`、`csf_generation`、`deduplication`、`descriptor_merge` 和 `csf_restore` 阶段的墙钟时间、Unix 进程 CPU 时间（平台可用时）、输入/输出记录数以及阶段边界的逻辑文件字节数。逻辑字节数不代表物理设备 I/O 或页缓存流量。
- **P0a 进度和输出契约**：range 进度通过 stderr 按约 2 秒限频报告 `started`、`completed` 和已生成 CSF 行数，不再用临时目录数量推断完成度。`--json` 的 stdout 仍是机器可解析的 JSON；新增 `stage_stats` 不改变既有统计字段。B0 维护测试覆盖统计、进度、V2 schema、行顺序、元数据和 round-trip，B1/B2 由显式基准脚本运行，不进入默认 pytest。
- **P1 统一执行选项**：内部 `GenerationOptions` 统一线程数、scratch 路径、批次设置和资源预算。现有 `--threads` 保持有效；Python 磁盘生成 API 追加 keyword-only 的 `memory_budget_mib`，PyO3、stub、TypedDict 和 CLI/TOML 配置同步支持。
- **P1 受管内存计量**：`memory_budget_mib` 约束占据组态、在途 Arrow batch、去重桶、幸存位图和 Parquet writer 的受管数据结构预留。预算不足会返回明确的资源错误；不会静默提高预算。每次运行通过 `resource_stats` 返回 `memory_budget_mib`、`budget_bytes`、`peak_managed_bytes`、`current_managed_bytes` 和 `occupation_bytes`。
- **预算边界**：该预算是内部字节记账，不是操作系统 RSS 硬限制；allocator 元数据、线程栈、Arrow/Parquet 运行库和其它进程内存不在其中。未指定预算时保持现有保守参数并报告未指定，不自动按物理内存百分比设置。
- **P1 有界生成和稳定发布**：range worker 直接写有界 segment，任务错误会在 join 后传播；segment 元数据携带 J/parity、range/segment 序号、记录数和字节数，merge 按稳定序号发布，因此 worker 完成顺序不改变结果，也不会因慢消费者保留完整 CSF batch。
- **V2 路径收口**：启用描述符的 TOML/config `csfsgenerate` 运行默认选择磁盘路径，直接生成可逆 V2 描述符，且磁盘路径禁止自动回退 V1；V2 的 `normalize=true` 明确拒绝。独立 `gen-descriptors` 仍可显式选择 V1。交互式 `csfsgenerate --generate-descriptors` 的旧 in-memory 兼容路径仍使用 V1，不属于本次 P0a/P1 迁移。

2026-09-22 评审修正（这些缺陷由评审发现，现有测试当时全部通过但没有覆盖相应路径）：

- **状态前缀合并会漏生成记录**：合并多个小前缀时任务区间只覆盖最后一个前缀，却计入
  整组记录数，早先的前缀不会被生成。已修正，并新增“任意任务切分下每个非空前缀恰好被
  覆盖一次”的回归测试（已验证该测试在旧代码上失败）。根因之一是原测试输入每个
  (组态, 2J) 至多一条记录，从未进入前缀拆分路径，现已换为会触发拆分的输入。
- **生成结束不再只相信计数**：实际记录数必须等于计数总量，每个超标组态的任务记录数
  必须等于其计数结果，切分错误直接失败而不是产出更短的文件。
- **空间预检按卷合并**：原实现分别检查各目录，同一卷上 scratch、staging 与发布副本
  各自通过而合计不足。现在按设备分组并按阶段取合计最大值。
- **无法读取可用空间时默认拒绝**（`allow_unchecked_space` / `--allow-unchecked-space`
  才继续），不再把未知当作通过。
- **估算不再拒绝计数回退的组态**，并按 2J 拆分后单独报告不可拆分长尾。
- **估算施加调用者的内存预算**，低预算估算与实际生成在同一阶段以同样原因失败。
- **空间开关语义收窄**（第二轮评审）：`allow_unchecked_space` 只覆盖"无法测量"，
  已知空间不足对任何准备写入的调用都拒绝；header 与描述符 sidecar 分别计入各自目标卷。
- **报告可审计性**（第二轮评审）：报告记录 `git.tree`、脏树 diff 哈希与已加载扩展的
  SHA-256，可从干净工作树复核；2026-09-21 的两份基线报告标注为早于该要求。
- **产物唯一性与脏源码**（第三轮评审）：同一 artifact kind 只能有一个目标（重复会重复
  计费，现在直接报错）；脏树指纹覆盖未跟踪文件并套用同一排除规则，且两个基准脚本
  默认拒绝在脏工作树上登记报告，`--allow-dirty-source` 才记为已标识的未提交测量。
  同时删除尚未接线的压缩抽象（P2a 接入时连同测量结论一起引入）。
- **源码身份前后快照**（第四轮评审）：身份在运行前采集并立即门禁，报告记录运行前快照，
  运行后再次采集并比较 commit/tree/dirty/扩展哈希，测量期间发生变化即拒绝登记；
  `git status` 改用 `-z` 结构化解析，覆盖带空格/引号/换行的文件名与 rename。
- **未跟踪目录完整性**（第五轮评审）：`git status` 加 `--untracked-files=all`，未跟踪
  目录内的文件改动必须改变指纹；目录条目递归哈希，不可读路径拒绝登记。

## 1. 目标与约束

目标是在 V2 结果及顺序不变的前提下，减少中间数据量、消除长时间串行后处理，并在明确的内存预算内提高多核吞吐量。

必须保持：

- 最终 V2 schema：每个 Peel 子壳层四列 `n/2j/v/2k`，另有 `total_two_j/parity`，均为 Int32。
- seniority、未打印值 `MISSING=-1` 与显式零的区别，以及已有 header 绑定和元数据契约。
- GRASP 文本格式、J/parity 块顺序、块内首条记录顺序、去重时保留首次出现者。
- 线程数、任务切分、批次大小、预算和临时压缩方式不改变逻辑结果。
- 外部数据的严格合法性检查；内部优化不能把未经验证的数据当成可信记录。
- 输出不得覆盖既有文件；失败不报告成功，不删除其他进程的文件。多文件发布不是天然的原子事务，不能通过文案宣称具备尚未实现的全组原子性。
- TOML/config 的默认磁盘描述符路径使用 V2；不能通过自动切回 V1 或旧归一化逻辑获得性能。V2 `normalize=true` 继续明确拒绝。交互式 in-memory 兼容路径的 V1 迁移尚未包含在 P0a/P1。

本计划不改变原子物理选择规则，不删除用户请求的输出，不把完整数十亿条结果放入内存，不要求维护测试依赖 GRASP 可执行文件或私有数据集。全面移除旧 V1 接口属于独立迁移任务。

### 2.2 规模与内存

使用当前库的真实占据枚举，并复用当前合法态表进行独立动态规划计数：

| 指标 | 基线结果 |
| --- | ---: |
| 唯一占据组态 | 7,031,941 |
| 每 range 4096 组态时的任务数 | 1717 |
| Peel 子壳层 / V2 列数 | 56 / 226 |
| 有序 `(kappa, occupation)` 模式数 | 270,592 |
| 去重前 CSF 计数 | 5,814,175,207 |
| 每 range CSF 数：最小 / 中位 / 最大 | 18,885 / 1,930,518 / 30,382,053 |
| 枚举及计数峰值 RSS | 3425 MiB，约 3.34 GiB |
| 枚举及计数墙钟时间 | 21.89 秒 |

完整输入未生成最终文件，58.14 亿是计数值，尚未逐条核验，也不是已经证明的去重后数量。计数在下述 B1、B2 上与真实生成数量一致。

当前临时 Arrow 每行是 `226×4+4+8=916` 字节数值载荷；完整输入约 4.844 TiB。根去重桶每行是 `226×4+8+16=928` 字节，约 4.907 TiB。源 Arrow 保留期间会写完整套根桶，两者合计约 9.75 TiB，尚不包括格式开销、递归分桶、文本和最终 Parquet。

即使不计临时列，58.14 亿行的 226 个 Int32 V2 值也有约 4.780 TiB 逻辑载荷。实际 Parquet 可能因 MISSING 长段、字典和 ZSTD 显著压缩，但在实测压缩比之前不能据此假定目标文件可以放下。P2 即使将 scratch 峰值降低 50%，也不自动证明完整任务可运行；还需同时计入最终 descriptor、CSF 文本、CSF Parquet、发布 staging、递归分桶写放大和文件系统安全余量。

1611 个 range 目录只能说明这些任务已经开始，不能视为已完成百分比。4.1 GB 用量也不能证明缓冲区充分利用了内存：枚举本身已有约 3.34 GiB 的峰值，且进程 RSS 和系统页缓存是不同指标。

2026-09-22 补充（P2a 测量）：上表中"逻辑载荷"是按未压缩 Arrow 计的，**segment 部分实测可压缩 43–92 倍**（B1 1073.0 MiB → 25.0/11.7 MiB，B2 506.0 → 8.2/4.5 MiB，见 [codec 报告](benchmarks/v2_disk_generation_codec_20260922.md)）。因此"4.844 TiB 源 segment"不是一个固定的空间需求，而是未压缩情形；根桶与递归桶（每行 928 字节）不走 Arrow IPC，压缩不触及，仍是按行宽计算的上界。

### 2.3 实际耗时

本地可见 8 个 CPU，工作目录位于 NVMe 文件系统；release 扩展，使用共享 Tools Python 环境。未清空页缓存，数据不代表用户服务器性能。

B1 保留参考组态与 2J，改用 `5s,5p,5d,5f,5g`、3 次激发：19,480 个组态、5 个 ranges、2,695,762 条 CSF。

| 阶段 | 1 线程 | 8 线程 | 8 线程复测 |
| --- | ---: | ---: | ---: |
| 枚举与 Arrow 生成 | 1.935 s | 0.681 s | 0.663 s |
| 去重 | 3.515 s | 3.548 s | 3.491 s |
| 合并描述符 | 2.083 s | 2.069 s | 2.037 s |
| 文本与 CSF Parquet 还原 | 5.034 s | 5.082 s | 5.037 s |
| 含启动的总耗时 | 12.681 s | 11.494 s | 11.346 s |

后三阶段的 CPU 时间各自接近墙钟时间，符合约一个 CPU 的占用。测量直接调用磁盘 API，不含 CLI 发布时的最终文件复制。B1 只有五个 ranges，不能据此推断大任务生成阶段的并行扩展性。

B2 使用完整活性空间、2 次激发：19,243 个组态、560,351 条 CSF。8 线程生成、去重、合并、还原分别约 0.244、1.500、1.034、1.184 秒。B1、B2 均未删除重复行，这不足以证明所有输入无需去重。

B1 中生成仅占端到端时间的小部分，去重、合并和还原合计约 10.6 秒。仅将这三段各自加速 2×，按 Amdahl 定律估算的端到端收益仍只是接近 2×，还会受启动、发布和 I/O 影响。因此阶段 2× 应作为调研目标，不作为不考虑端到端收益的绝对发布条件。

## 3. 分阶段交付

建议依赖和决策顺序：

P0a 与 P1 已完成，P6a 已给出结论（内部路径全局唯一，P3 不适用）。剩余顺序为 `P0b → P5a → P1.5`，之后进入 `P2a → P2b → P4`。P2b 对内部路径只需保留稳定顺序发布所需的暂存，不为已证明无用的根桶投入格式优化。之后完成 `P5b` 生成优化，最后由 `P6b` 在证明和回归门槛通过后启用快速路径。

### P2：减少暂存数据与分桶 I/O

改动范围：内部 segment codec、`streaming.rs` 的 writer/reader/桶记录格式。

分为两个可独立验收的子步骤。P6a 若已证明某些内部生成路径无需全局去重，P2 对这些路径只保留稳定重排和最终输出所必需的暂存，不再为已证明无用的根桶优化格式。

- [x] **P2a：临时 Arrow 压缩限时实验。** 比较当前无压缩、依赖实际支持的 LZ4/ZSTD；确认 Arrow IPC feature 配置，测 CPU、编码速度、写入量和峰值内存。协议显式记录 codec，不能把尚未启用的压缩当成有效设置。该步骤是决策实验而非长期架构投入；若紧凑记录明显取代密集 Arrow，保留测量结论即可。**结论（2026-09-22，[报告](benchmarks/v2_disk_generation_codec_20260922.md)）**：`RCSFS_SEGMENT_CODEC` 选择 codec，扩展回报实际写入的 codec，基准脚本核对不一致即失败；`arrow-ipc` 的 `lz4`/`zstd` feature 均已启用。B1 的 segment 由 1073.0 MiB 降到 25.0（lz4）/11.7 MiB（zstd），B2 由 506.0 降到 8.2/4.5 MiB；scratch 峰值相应减少约 50%（B1 2142.5 → 1081.2 MiB，B2 1001.9 → 500.4 MiB）。端到端代价 zstd 为 +4.2%/+7.1%，lz4 为 +16.7%/+23.1%，差异都在**读取侧**（去重与合并的解压），写入侧生成阶段几乎不变。**zstd 优于 lz4**。默认值保持不压缩，本阶段只登记结论。
- [ ] **P2b：紧凑暂存记录。** 重用整数记录语义，按 batch 存储占据子壳层、合法局域态、耦合 arena 及记录 offsets；省略未占据槽位，保留 MISSING 和 seniority。内存中不为每条记录创建多个独立 Vec。P2a 之后本项的目标需要重新表述：B2 的 scratch 峰值已因 segment 压缩减半，**剩余的一半全部是 226 列根去重桶**，而 P6a 已证明内部路径不产生重复行——对内部路径，紧凑记录的正确定位是"随 P6b 一起取消根桶"，而不是为根桶发明更省的格式。
- [ ] range ID 等批次常量放到 segment 元数据，连续 ordinal 尽量存 base/count；读取时仍验证连续性和范围。
- [ ] 去重 key 从规范化紧凑记录产生，哈希碰撞后仍精确比较。用于比较的全局 Peel 映射必须相同，不能把不同配置的局部下标直接比较。
- [ ] 对 P6a 判定仍需精确去重的路径，分桶文件也使用紧凑记录/有界块；不能只压缩源 Arrow，却继续写完整 226 列根桶。P6a 已判定内部路径全局唯一，因此内部路径的根桶应随 P6b 整体取消，而不是先用紧凑格式优化再取消；本项只适用于将来仍需保留精确去重的路径。
- [ ] 物理 segment 按目标字节聚合，不因后续调度变细而生成大量小文件。内部格式带版本号，本阶段不承诺旧 scratch 断点恢复。

完成条件：新旧暂存路径在 B0/B1/B2 上输出相同文本和 V2 逻辑行；损坏 offsets/截断文件明确失败；记录临时空间、逻辑 I/O 与 CPU 代价。B2 暂存峰值空间降低至少 50% 作为默认启用目标；未达目标则记录原因并继续实验，不直接宣称完成优化。**2026-09-22 状态：该 50% 目标已由 P2a 的 segment 压缩单独达成**（B2 1001.9 → 500.4 MiB），但达成方式不是紧凑记录，且剩余峰值全部是根桶。因此本阶段的验收改为：P6b 取消根桶后，B2 的 scratch 峰值应降到 segment 量级（当前 zstd 下为 4.5 MiB 量级）；紧凑记录只在仍需保留精确去重的路径上验收。同时用 P1.5 的模型估算 B3 峰值；“B2 降低 50%”不能单独作为 B4 可启动的证据。

完成条件：生成流程中没有读取刚写出的最终 descriptor 以还原文本；线程数变化不改变 CSF 字节及 V2 行；发布竞争测试作用于真实新路径。B1/B2 上并行转换阶段目标至少 2× 加速，累计端到端相对 `7ad18b1` 的 8 线程基线目标至少 2×。这些是调研和验收目标，不是无条件发布承诺；若未达目标，按端到端收益、I/O 减少、峰值空间和统计波动决策。

### P3（条件阶段）：去重全链路并行化（**不适用**：P6a 已证明内部路径全局唯一）

启动条件：P6a 发现一般反例，或只能将精确去重缩小到仍然构成显著瓶颈的边界。若 P6a 已证明内部路径全局唯一，不实施无用的根桶并行化，并在决策记录中标记 P3 不适用。**2026-09-22 决策：P6a 给出的是“内部路径全局唯一”，且没有第二种情形——不存在“缩小到仍然构成显著瓶颈的边界”，因为内部路径一条重复都没有。P3 标记为不适用，本节以下各项不实施**（保留原文以记录当时的判据）。将来若出现本证明范围之外的输入路径（例如外部 CSF 文本路径的去重需求），该结论不自动适用。

改动范围：分桶、递归拆桶、幸存索引、并行执行管理。

- [ ] 对 segment/batch 并行计算规范化 key 和 hash，将结果送往有界 bucket 写入任务，避免每行竞争全局锁。
- [ ] 显式携带原始稳定 ordinal，桶写入顺序可以变化；同 key 的 survivor 取最小原始 ordinal，不能取最快 worker 的记录。
- [ ] 根据预计字节量和预算规划桶数、叶桶容量及并发数，替代全场景固定 65,536 行；分桶决定仅影响执行方式，不影响输出顺序。
- [ ] 并行消费互相独立的桶；使用局部幸存索引或分区位图归并，避免每个 worker 都复制一份完整 bitset。
- [ ] 超大桶按确定性规则进一步拆分。对大量完全相同 key 单独处理，不能无限依赖再次 hash 将它们分散。
- [ ] 用较大的有界 I/O buffer 合并小写入；哈希先保持确定性，是否替换 SHA-256 作为单独微基准决策，精确比较始终保留。

完成条件：单 J/parity 也能并行；跨 segment/线程/递归层的重复、强制碰撞、全部相同行和乱序任务均保持首次出现记录。B1/B2 以及专用去重压力样例在 8 个可用 CPU 上相对新实现 1 线程达到至少 2× 加速作为目标，并报告相对旧版本的绝对耗时、I/O 和端到端收益。未达目标时先定位瓶颈，再根据统计显著性、端到端收益和空间收益决策，不以阶段 CPU 占用率单独决定发布。

### P5b：目标 J 剪枝、角动量缓存和生成存储优化

改动范围：`states.rs`、`mod.rs`、`descriptor_schema.rs`、`occupations.rs`、内部生成 batch。计数和 range planner 已前置到 P5a。

- [ ] 合法态表改为可复用只读数据；Peel 标签只解析一次。外部验证继续使用完整规则，但通过缓存查表而非逐记录分配 Vec。
- [ ] 建立目标-J 的后缀可达位集/DP，对无法完成的耦合前缀提前剪枝，保留其余分支的原始遍历顺序。
- [ ] 缓存键包含有序角动量/占据模式、目标 2J 范围及影响输出的状态语义；主量子数、Peel 映射、parity 在构建最终记录时正确补回。先缓存小型状态/DP，不缓存所有 CSF 模板。
- [ ] 替换嵌套并行中无限增长的完整分支 Vec，使用 P1 的有界 batch；外层任务充足时避免对所有配置再做大量细粒度并行。
- [ ] 占据组态与排序 key 改为紧凑 arena/共享存储，合并时尽量移动而非克隆；不改变 reference 合并顺序。若完整组态仍不能放进指定预算，明确失败；外部排序/spill 作为独立后续任务，不伪称已经支持。
- [ ] 使用实际产出记录的 used-orbital bitmap 收口 Peel header，覆盖合法配置但零目标-J 产出的情况；不让预枚举的未使用轨道破坏 header 等价性。

完成条件：剪枝开关、缓存开关、线程数和 P5a 切分方式不改变顺序；缓存不超预算；零目标-J 产出组态的 Peel header 与真实输出记录一致。单独报告生成 CPU 收益和端到端收益，不以局部剪枝收益代替 P2/P4 的 I/O 改造。

压力场景包括：最早任务极慢、后续任务快速完成、零产出任务、单一超大配置、重复倾斜桶、强制哈希碰撞、超过 2^32 的 ordinal 小型合成边界、截断临时文件、写入异常、发布竞争、预检后可用空间变化和恢复 manifest 与输入哈希不匹配。

性能基准每个组合预热 1 次、测量至少 3 次，报告中位数及波动，并保留执行顺序以识别页缓存偏差。比较线程 1/2/4/8（以及目标机器适用的更高值），预算至少取低/中/高三档；预算不足组态基线时应报告资源拒绝，不能用其伪造慢速基线。记录缓存条件、CPU 配额、RSS、受管内存、逻辑 I/O、可获得时的物理 I/O、scratch 峰值、文件数和最终产物大小。

同机比较的默认启用门槛：正确性与资源约束全部通过，目标阶段有可重复实测收益，B0/B1/B2/BD/BS 的适用集合不出现无法解释的端到端性能回退。超过 10% 的稳定回退需明确处理或保持旧策略可选，不能仅以 CPU 占用更高解释。单阶段 2× 和端到端 2× 是调研目标；未达到时依据统计波动、端到端耗时、峰值空间、写放大和复杂度综合决策，不作为脱离 workload 的绝对门槛。
