# P2a：临时 segment 的 Arrow IPC 压缩实验（2026-09-22）

本文登记 [CSF_V2_GENERATION_PERFORMANCE_PLAN.md](../CSF_V2_GENERATION_PERFORMANCE_PLAN.md)
P2a 的限时实验：临时 Arrow IPC segment 不压缩、LZ4_FRAME、ZSTD 三者的耗时、写入量、
CPU 与受管内存。这是决策实验，不是长期架构投入。

测量来自**干净工作树**的提交 `3588df1`（tree `fdae74cc1a9e…`），release 扩展，其
SHA-256 为 `cbcf2eb87309…`（两个哈希都记录在 JSON 的 `environment.git.tree` 与
`environment.extension.module_sha256` 中，可重建后比对）；Apple M4 10 核 16 GiB，
APFS；8 线程；每个 codec 各预热 1 次后测量 3 次，codec 之间顺序执行（`none → lz4 → zstd`），
表中为中位数。可以说明这不是页缓存偏差：zstd（最后执行）的端到端中位数仍低于 lz4
（先执行），而两者的 segment 写入量相差不到 2 倍。

本报告生成时所有组合仍在同一 Python 进程中顺序运行，原始 JSON 的 `rss_peak_bytes` 是
`ru_maxrss` 的进程生命周期高水位，不能比较 codec 的独立 RSS；因此本文没有据此给出峰值
RSS 结论。harness 后续已改为每次测量使用独立进程，本阶段需在干净提交上重测 RSS 后才能
完成“峰值内存”验收。

## 结论

1. **segment 字节压缩 43×–92×**（B1：1073.0 → 25.0/11.7 MiB；B2：506.0 → 8.2/4.5 MiB）。
   这是密集 Int32 载荷加上大量 `MISSING`（`-1`）与低基数字段的典型结果，不是通用比例：
   它只说明"临时 Arrow 不值得按未压缩体积规划"，不说明任意输入都能达到同样倍数。
2. **scratch 峰值降低约 50%**（B1 2142.5 → 1081.2 MiB，B2 1001.9 → 500.4 MiB）。
   降低的部分正好是 segment 那一半；剩下的一半是 226 列根去重桶，压缩不触及它。
3. **zstd 优于 lz4**：同样的 scratch 峰值，端到端只高 4.2%（B1）/ 7.1%（B2），而 lz4 高
   16.7% / 23.1%。差异全部落在读取侧：B1 去重阶段的 CPU 由 3.479 秒（none）升到
   4.622 秒（lz4）与 3.787 秒（zstd），合并阶段由 2.789 秒升到 4.220 秒与 3.390 秒。
   写入侧几乎不变——生成阶段的墙钟与 CPU 三个 codec 基本相同（B1 0.703–0.738 秒、
   CPU 5.45–5.52 秒；B2 0.243–0.282 秒、CPU 1.54–1.61 秒），说明这些数据的压缩成本低于
   少写近 1 GiB（B1）的收益。
4. **默认保持不压缩**：本实验只回答"压缩是否有价值"，默认值与容量模型都不改动，
   启用与否由后续阶段（P6b 取消根桶之后重新评估）决定。

## 未测量

- 每个 codec 独立的进程 RSS 峰值；旧 JSON 中的 RSS 是共享进程的单调高水位。
- 目标机器与目标文件系统；本机为 NVMe/APFS、页缓存未清空，`process_io` 在 macOS 上
  不可得，因此表中没有物理 I/O 与写放大。
- 根去重桶与递归桶的压缩（两者都是自描述行格式，不经过 Arrow IPC）。
- 其他压缩级别：`arrow-ipc` 使用 LZ4_FRAME 默认参数与 zstd 默认级别，未做级别扫描。
- B3 规模：该实验只跑了 B1/B2，因为 P2a 是限时决策实验。
